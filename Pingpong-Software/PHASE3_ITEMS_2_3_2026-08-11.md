# PHASE 3 — Items #2 & #3 (2026-08-11)

## Item #2 — Backgrounding / resume: FIXED (client-side, verified by static read)

**Found:** `document.addEventListener("visibilitychange", ...)` only ever
called `requestWakeLock()` — nothing re-validated the mic track or the
voice connection on resume.

**Root cause:** on real mobile browsers (most reliably iOS Safari; Android
under memory pressure can do the same), a long background period can end
the `getUserMedia` `MediaStreamTrack` outright (`readyState` becomes
`"ended"`), not just drop the socket. `localStream` keeps referencing that
dead track object. Neither the mesh path's `ensureLocalTracksSent()`
(checks "is there a sender", not "is the track alive") nor the SFU
seated-speaker self-heal added in item #1 checks track health — both only
check "do we have a `localStream`". Net effect: after a real background
period, a seated speaker can resume with a technically-non-null
`localStream` that can never actually carry audio again, and nothing
would have noticed.

**Fix (`public/app.js`, inside the existing `visibilitychange` listener):**
on becoming visible again, while seated and in a room, check the current
mic track's `readyState`; if `"ended"`, clear `localStream` and re-run the
exact same `initMicIfNeeded()` + `ensureLocalTracksSent()` path a normal
seat-take already uses — this re-acquires a real track and reconnects
(mesh renegotiation or SFU publish, whichever mode is active).

This is layered under the existing, separately-verified Socket.IO
reconnect path (`reconnectionAttempts: Infinity` → `socket.on("connect")`
→ `rejoinRoom()` → server `room-state` push → item #1's SFU self-heal /
mesh's `ensureLocalTracksSent()`), which was already sound — this fix
only closes the "track itself died" gap that the socket-reconnect path
alone couldn't detect.

`node --check public/app.js` passes. **Not verified on a real device** —
needs a genuine backgrounding test (iOS Safari and Android Chrome/WebView,
several minutes backgrounded) to confirm the track actually does end in
your target environments and that this recovers it.

## Item #3 — TURN-only / restrictive NAT: AUDITED, no code bug found

**Mesh voice:** `turn-config.js` → `/api/calls/ice-servers` → room-voice
`RTCPeerConnection` (`public/app.js` line ~3721) is wired correctly —
`iceServers` includes both STUN and TURN entries when `TURN_URL`/
`TURN_SECRET` are set, and `iceTransportPolicy` is left at its WebRTC
default (`"all"`), which is the *correct* setting for restrictive-NAT
reliability: the ICE agent automatically falls back to relay (TURN)
candidates when direct/STUN candidates fail, with no code change needed.
Forcing `iceTransportPolicy: "relay"` would be wrong here — it would
force TURN for every connection, wasting TURN bandwidth for the common
case where direct connectivity works fine.

**SFU (LiveKit) voice:** deliberately does not go through `turn-config.js`
at all — `voice_sfu/livekit.js`'s own header already documents this:
LiveKit (self-hosted or LiveKit Cloud, which your credentials indicate
you're using) handles its own ICE/TURN relay internally on the
media-server side. This is correct architecture, not a gap.

**Conclusion:** nothing to patch here. What's actually needed is a real
restrictive-NAT device test (e.g. a phone on a carrier network known to
block UDP, or with `iceTransportPolicy` temporarily forced to `"relay"`
in a debug build to simulate TURN-only) — a network-condition test, not a
code fix, and one this sandbox cannot perform (no network egress).
