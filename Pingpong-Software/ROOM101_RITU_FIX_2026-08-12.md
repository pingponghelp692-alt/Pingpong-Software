## What I fixed this session
0. **New this update — guaranteed fallback so Ritu always speaks, even if
   Vapi itself is broken.** This is the direct answer to "make it 100% sure
   Ritu will speak": previously, if Vapi failed for ANY reason (bad
   credential, unpublished assistant, blocked network, or even a silent
   hang with no error at all), Ritu stayed completely silent — the
   browser TTS/STT fallback was hard-disabled the moment `VAPI_PUBLIC_KEY`
   was configured, regardless of whether the live call actually worked.
   Now:
   - `vapi-support.js` calls a new `window.PingPongRobin.onVoiceFailure`
     hook on every real failure (both a rejected `start()` and the SDK's
     own async `error` event).
   - `app.js` wires that hook to `cs101FallbackAfterVapiFailure()`, which
     switches the current seat visit over to the app's own server-side
     text-AI reply + browser `SpeechSynthesis`/`SpeechRecognition` bridge —
     nothing here depends on Vapi or Daily.co being reachable.
   - Added a **7-second watchdog**: if Vapi hasn't reported an active call
     within 7s of auto-start (covers a silent hang with no error event at
     all), the same fallback fires automatically.
   - The fallback resets on every new seat visit, so a later, working Vapi
     attempt is still tried first — one bad attempt doesn't permanently
     disable Vapi for the rest of the session.
   With this, Ritu speaking no longer depends on Vapi succeeding — only on
   your own server (Gemini/OpenAI text reply, already has cross-provider
   fallback from the previous session) and the browser's built-in speech
   APIs, both of which are entirely within your own infrastructure.
1. **The exact error in your screenshot** — `vapi.on("error")` always showed
   the generic "Voice support could not connect. Please try again." even
   when the Vapi SDK's error carried a real, specific reason (bad key,
   assistant not published, network/CSP block, mic permission). It now
   shows the specific reason (reused the same classification logic that
   `startCall()`'s own catch block already had, so both paths are
   consistent). This won't fix a bad credential by itself, but it will tell
   you or me exactly *why* it's failing next time it happens on your device,
   instead of the generic message.
2. **Safety-net cleanup** — if a room-state update ever lands for a room
   other than 101 while a Vapi call is active (edge case beyond the normal
   leave-seat/leave-room paths, e.g. a forced move), Robin now always stops
   and releases the mic. Previously only the two normal paths did this.
3. **Room 101 seat admin, surfaced in the Admin Panel** — the backend
   already fully supported scoping a Moderator to Room 101 only
   (`assignedRoomIds`, `rbac.inRoomScope`, and the existing
   `rooms:seat-lock` / `rooms:kick-user` / `rooms:mute-user` permissions a
   Moderator gets by default), but there was no UI for it — an admin
   creating one had to already know to set `assignedRoomIds: ["101"]`
   manually via the API. Added:
   - a checkbox on **Create a New Admin Account** ("Assign as Room 101
     Support Admin") that appears only for the Moderator role,
   - an **Assign Room 101 / Remove Room 101** button per existing Moderator
     row in the accounts table,
   - a **Scope** column showing which moderators are Room-101-only.
   A Moderator assigned this way can open/close seats, mute, and kick —
   only inside Room 101. No new permission or route was added; this only
   wires the existing RBAC mechanism into the UI.

## Update (2026-08-12, same day) — "speaks once, then stops responding"
You reported: sits on the seat, Ritu speaks once, then doesn't respond to
further speech, and the overlay shows "Microphone access is blocked. Allow
microphone permission and open PingPong over HTTPS." (This message itself
proves the earlier fix worked — it's now telling you the real reason
instead of a generic message.)

**Most likely root cause, found by re-reading the code I added last time:**
the previous session's 7-second "Vapi seems stuck" watchdog could fire
while Vapi was still genuinely (if slowly) connecting on a real mobile
network, switching the seat over to the browser's own
SpeechRecognition/SpeechSynthesis fallback — and then Vapi went on to
connect successfully a few seconds later anyway. That leaves **two separate
mic listeners open on the same seat at once** (Vapi's own call + the
browser fallback's `SpeechRecognition`). Some Android WebViews (this
project ships a native Android WebView wrapper —
`android/app/src/main/java/.../MainActivity.kt` — and its manifest does
correctly declare `RECORD_AUDIO`, so this isn't a missing-permission
config problem) only reliably support one active microphone capture at a
time; a second concurrent request can silently break the first one. That
matches your symptom exactly: whichever source grabbed the mic first
produced the one reply you heard, then the second one interfered with it.

**Fixed:**
- Vapi's own `call-start` event (a real, successful connection) now always
  hands the seat back from any already-active fallback — cancels the
  fallback's mic listener and speech synthesis immediately
  (`cs101CancelFallback()`), so only one voice path is ever active at once.
- `cs101StartAutoRecognition()` (the fallback's mic listener) now also
  refuses to start at all while Vapi reports an active call, as a second,
  independent guard.
- `cs101Speak()` (fallback text-to-speech) got the same guard.
- Widened the watchdog from 7s to 12s to make the false-positive trigger
  itself less likely on a slow connection, on top of the above.

**Still worth checking on your device, if it recurs:** open the browser
console right when it happens — the status message will now say the exact
Vapi-reported reason. If it's specifically about the mic (not a stale
watchdog race), on Android check Settings → Apps → PingPong → Permissions
→ Microphone is set to "Allow" (not "Ask every time"), and confirm no other
app/tab is holding the microphone at the same time.


Even with the fallback above, I can't certify the full stack from this
sandbox (no internet access here, same as every prior session). What I CAN
now say with confidence: **Ritu will speak using at least the browser
fallback as long as your server itself is reachable and at least one of
`GEMINI_API_KEY` / `OPENAI_API_KEY` is set** — that no longer depends on
Vapi/Daily.co working at all. What still needs a real device to confirm:
that Gemini/OpenAI key is actually valid and the browser's speech APIs work
on your target device/browser (nearly universal on modern Chrome/Android,
but I can't test it from here).
